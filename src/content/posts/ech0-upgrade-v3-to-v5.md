我自托管的这个小站跑的是 Ech0，一个开源、轻量的个人微博客平台。某个周末例行检查时，我发现它停在 v3.1.2，而官方已经发到了 v5.7.0——中间整整跳过了两个大版本。跨版本升级最怕的就是数据出问题，所以我一边备份一边慢慢来，把整个过程记录下来，也顺便聊聊踩过的坑。

## 升级前：先把家底摸清楚

升级的第一件事不是动手，而是搞清楚「我现在到底跑的是什么」。

我用 Docker Compose 部署的，先查容器和镜像拿到了几个关键信息：

- 当前版本：`v3.1.2`，镜像取自官方仓库的 `latest`
- 数据都挂在宿主机的一个目录下，SQLite 数据库和图片、音频、密钥都在里面
- 用的是自定义 bridge 网络，固定了一个容器 IP

这里有个判断很关键：`v3.1.2 → v5.7.0` 不是普通的小版本更新，中间跨了多个破坏性变更。比较明显的几个：

- `v5.0.0` 把「备份」全面改名成「快照」，磁盘路径、设置项、接口路由、事件名全变了，而且**不是自动迁移**的
- `v5.4.2` 把本地密码从裸 MD5 换成了 bcrypt，但设计成「惰性」的，要等用户首次登录才真正切过去
- `v5.4.4` 把 SQLite 切成了 WAL 模式
- `v5.4.7` 把内置 MCP 协议升级到了新版本，对老的 MCP 客户端不兼容

所以这次不是「拉个新镜像重启」那么简单的事。

## 备份：宁可多此一举，不可追悔莫及

跨大版本升级，数据永远是第一位的。我在动手前做了完整备份：

1. **先停容器**。这一点很重要——不停容器直接打包，SQLite 在写入中的文件可能不一致，归档出来是坏的。
2. 把整个数据目录打包成 `tar.gz`。
3. 解压校验一遍，确认里面的数据库、媒体文件、密钥、旧备份都在。

备份做完心里就有底了，万一升坏了随时能回滚。

## 升级：标准流程，顺带观察迁移

官方文档给的标准升级路径很干净：

```bash
# 拉最新镜像
docker pull sn0wl1n/ech0:latest

# 进入 compose 目录，强制重建容器
docker compose up -d --force-recreate
```

重建完成后，我盯着启动日志看它怎么迁移数据库。结果很顺利：

- 时区字段做了规范化，把历史数据的时间统一到服务器时区
- 旧版本的定时备份任务按预期被清除了（这是 `backup → snapshot` 更名的副作用）
- 表结构已经升到新版本，新增了一堆表，旧的遗留列也删掉了

数据库里原本的内容一条不少：用户、动态、评论都在。

但当时我以为"迁移顺利完成"下结论太早了——真正的大坑藏在这里：

```
[2026-08-28T11:07:56Z][error]datatype mismatch
```

升级后不久，后台创建访问令牌时报了这个错。SQLite 报 `datatype mismatch`，日志里却只有孤零零一句话，没有任何 SQL 和堆栈。

## 踩到的坑：三个值得说的地方

### 1. 「备份」变成了「快照」，定时备份会重置

这是 `v5.0.0` 最大的破坏性变更。以前配的定时备份设置，升级后直接被清空了——这不是 bug，是官方故意的重命名，但坑就坑在它**不会自动迁**。升级完我进后台一看，定时快照是关的，得手动重新开启。如果没注意到，数据就一直在裸奔。

### 2. 密码迁移是惰性的，别以为就完事了

`v5.4.2` 把密码从 MD5 换成 bcrypt，但因为它没法把 MD5 反推回明文再加密，所以设计成「首次登录时自动重算」。也就是说，升级完数据库里密码算法字段还是 `md5`，要等用户用真实密码登录一次，程序验证通过后才会悄悄改成 `bcrypt`。

我一开始以为迁移没跑完，后来翻文档才明白这是预期行为，不是故障。

### 3. 登录接口的路径变了

升级完我用老路径测登录，结果 404。查了一下才发现老版本是 `/api/auth/login`，新版本改成了 `/api/login`。接口路径变更这种事，只有自己踩一遍才记得住。

### 4. 最大的坑：主键从整数变成了 UUID

创建访问令牌的 `datatype mismatch` 排查起来很费劲。我把表结构和上游源码翻了半天，终于定位到根因：

**v5.7.0 把一批表的主键从整数改成了 `char(36)` UUID**——`User`、`Echo`、`Tag`、`Webhook`、访问令牌等全都改了，创建记录时用 UUIDv7。但 GORM 的 `AutoMigrate` **不会修改已经存在的主键列类型**，所以从 v3.1.2 带来的 `integer PRIMARY KEY AUTOINCREMENT` 原封不动。新代码往整数主键里塞 UUID 字符串，SQLite 就报 `datatype mismatch`。

更麻烦的是，官方在 2026 年 4 月的一次提交里**移除了 v3 原地迁移支持**——v3 升 v4 本来就是导出导入的流程，官方压根没打算让你直接把 v3 的库扔给 v5 跑。我这种"跨两个大版本硬升"的路径，主键转换只能自己动手。

手动迁移的活儿不难但琐碎，要点就三句：

1. **有数据的表重建**：把 `users`、`echos`、`tags`、`echo_tags` 重建为 `char(36)` 主键，旧整数 id 逐个映射成 UUID，顺带把引用这些 id 的列（`user_id`、`echo_id`、`tag_id` 等）一起换掉。
2. **空表直接删**：`connecteds`、`webhooks`、访问令牌、passkey 这些表没有数据，删掉让应用启动时按新 model 自动重建，最干净。
3. **先演练再动手**：SQLite 重建表有个坑——索引名是全局的，`RENAME TABLE` 之后旧索引还占着名字，不先 `DROP` 的话 `CREATE INDEX` 会撞名。我先在数据库副本上跑了一遍脚本，把这个问题修掉，才在生产库上执行。

迁移时我还顺手发现并修了两个隐藏问题：迁移前用户表的 `is_owner` 是 NULL（v3 遗留，会导致 owner 判断失效），补成了 1；以及 WAL 模式下直接 `cp` 数据库文件拿到的是不含 WAL 数据的旧副本，必须用 `sqlite3 .backup` 或者先 `wal_checkpoint` 再做一致性快照。

### 5. 媒体文件：v3 的 images 表 v5 不认了

主键迁完，访问令牌能建了，但很快又发现另一件事：**有几条动态的配图消失了**。

排查下来是媒体存储机制的变更。v3 把图片信息放在 `images` 表里，文件存在 `data/images/` 目录；v5 全面改成了 `files` + `echo_files` 两张表，文件静态根目录也换成了 `data/files/`，图片 URL 变成 `/api/files/images/<key>`。数据库升级不会自动把 `images` 表的记录搬到新体系，所以老图在前端就「看不见」了——哪怕文件还好好躺在磁盘上。

修法也不复杂，就三步：

1. 把老图片文件从 `data/images/` 复制到 `data/files/images/`
2. 在 `files` 表补记录（`storage_type=local`、`category=image`、`url` 指向 `/api/files/images/...`）
3. 在 `echo_files` 表把图关联回对应的动态

这里有个容易踩的误判：升级后你 `curl` 老地址 `/images/xxx.webp` 可能照样返回 200，很容易以为「图片没丢」。但那其实是前端 SPA 的兜底页面，`Content-Type` 是 HTML 不是 `image/webp`。判断静态文件到底有没有被正确服务，一定要看响应头里的 `Content-Type`，别被 200 骗了。

## 升级后的验证清单

我给自己列了个检查表，逐项确认：

- 服务正常启动，版本号显示 `v5.7.0`
- 首页能访问，返回 200
- 端口正常监听
- SQLite 已经进入 WAL 模式（出现了 `-wal` 和 `-shm` 伴生文件）
- 数据库里的用户和动态数量跟升级前一致
- 用错误密码调登录接口，返回的是「密码错误」而不是 500——说明用户识别和密码校验链路都是好的
- 主键迁移后所有相关表的主键都是 `char(36)`，创建访问令牌不再报 `datatype mismatch`
- 媒体迁移后 `/api/files/images/...` 返回 200 且 `Content-Type` 是图片类型，老动态配图正常显示

## 一点经验总结

跨大版本升级，最值的投资就是把升级前的「侦察」做扎实：

1. **先确认当前版本和部署方式**，别想当然。
2. **翻一遍 Release Notes / Changelog 里的 Breaking Changes**，尤其是注明「不自动迁移」的那几条。
3. **备份时先停服务**，保证数据文件一致性。
4. **升级后盯着启动日志看迁移**，而不是只瞄一眼「服务起来了」。
5. **留好回滚路径**——只要数据目录完整，随时能退回旧镜像。
6. **读源码而不是只看文档**：`datatype mismatch` 这种错误日志极其简洁，最终是拿上游 model 定义和实际表结构逐一对比才定位到主键类型不一致的。

这次折腾下来，最大的收获是理解了「自托管软件跨版本升级」的通用套路：先侦察、再备份、小心迁移、仔细验证。而跨版本跳得越远，越不能指望自动迁移帮你搞定一切——`AutoMigrate` 会加新表新列，但**改主键类型、迁移媒体关联这些事它不干**，数据库结构的历史包袱得你自己背。数据安全永远比「快点升上去」重要。
